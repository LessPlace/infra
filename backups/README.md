# Резервное копирование продакшена Less

Скрипты выгружают PostgreSQL с обеих действующих ВМ и все бакеты выбранной папки
Yandex Cloud на эту машину, затем проверяют локальное восстановление баз и целостность
файлов S3. Рабочие локальные базы сохраняются. Промышленные операции выполняют только чтение.

## Запуск

Из корня проекта:

```sh
infra/backups/backup-all.sh
# Или с новым каталогом назначения:
infra/backups/backup-all.sh /absolute/path/to/new-backup
```

Нужны Python 3.9+, Docker с образом `postgres:18`, `ssh`, авторизованный `yc` с выбранной
папкой Less `b1gk1vp06cum61i9d4fe`. Права оператора: SSH и `sudo -n docker` на обеих ВМ;
чтение конфигураций, объектов, версий, ACL и меток всех бакетов. IAM-токен берётся через
`yc iam create-token`, остаётся в памяти, обновляется через 30 минут. При истечении
сеанса `yc` может потребовать вход через браузер. Новые ключи и облачные ресурсы не создаются.

По умолчанию копия появляется в `output/production-backups/<UTC-время>/` вне репозитория
infra. Существующий каталог не перезаписывается. Каталоги имеют права 0700, файлы — 0600.
**Дампы содержат пользовательские данные и пароли ролей PostgreSQL.** Не добавлять их в Git;
для переноса на другой носитель использовать шифрование. Локальная копия сама не зашифрована.

Признак полного успеха — файл `COMPLETE`. Если операция оборвалась, каталог остаётся для
диагностики, но не объявляется готовой копией. Повторный запуск требует нового каталога.
Вывод внешних команд при ошибке скрыт, чтобы не раскрыть данные и секреты.

## PostgreSQL

- В `postgres/manifest.json` записаны все БД, кроме шаблонов из `pg_database`, в том числе `postgres`.
  Шаблоны `template0` и `template1` не копируются; проверка использует штатные шаблоны PostgreSQL 18.
- Для каждого сервера сохраняются `globals.sql` (роли с паролями, членство и табличные пространства)
  и полные архивы `pg_dump --format=custom --create` с данными, схемой, владельцами и правами.
  Все базы, кроме шаблонов обнаруживаются при каждом запуске, имена не зашиты в скрипт.
- Дамп каждой БД и контрольные количества строк используют один экспортированный снимок
  транзакции. Строки обычных таблиц и материализованных представлений проверяются после восстановления.
  Для разных БД и S3 нет общего атомарного снимка: запись пользователей во время копирования продолжается.
- Проверка создаёт отдельный новый контейнер для каждого сервера, без сети и опубликованных портов,
  с новым анонимным томом и случайным административным пользователем. Восстанавливаются роли,
  затем каждая БД с `pg_restore --exit-on-error --clean --if-exists --create`.
  Ошибка SQL или несовпадение числа строк останавливает проверку.
- Контейнеры проверки и только их анонимные тома удаляются в `finally`. При аварийном завершении
  процесса контейнер с меткой `less.backup-verification=true` может остаться: осмотреть его
  перед ручным удалением. Рабочие контейнеры скрипт не выбирает и не удаляет.
- Отчёт `postgres-restore-report.json` сохраняется рядом с каталогом PostgreSQL.
  Это доказательство восстановления схемы, данных, ролей и прав без SQL-ошибок и сверки количества
  строк, а не полная побайтовая сверка значений и не запуск приложений на восстановленных БД.
- Лимит проверочного контейнера — 1 CPU / 1 ГиБ памяти; данные размещаются на диске Docker.
  Требуется место под копию и последовательное восстановление крупнейшего сервера.
  Нестандартные табличные пространства и версия сервера, отличная от 18, требуют доработки;
  скрипт явно останавливается. Новые ВМ добавляются через `--hosts hosts.json`.

Отдельная повторная проверка уже скачанной копии:

```sh
python3 infra/backups/postgres.py verify /absolute/path/to/backup/postgres
```

## S3

- `yc storage bucket list` обнаруживает все бакеты в выбранной папке. Пустой список и
  посторонние имена без префикса `less` завершают операцию ошибкой.
- Сохраняются полная конфигурация Yandex Cloud и ответы S3 для ACL, политики, CORS, жизненного
  цикла, меток, версионирования, сайта, уведомлений, журналирования, шифрования и блокировки объектов.
  Отсутствующая или неподдерживаемая настройка отмечается отдельно. Отказ доступа не пропускается.
- Опись `ListObjectVersions` проходит все страницы; скачиваются все доступные версии, включая
  `null`, сохраняются маркеры удаления. Для каждой версии сохраняются заголовки ответа
  (включая пользовательские метаданные), ACL, метки, размер и SHA-256.
- Объекты лежат в `s3/<бакет>/objects/<SHA-256 идентичности>/data`. Точное исходное имя и версия —
  в соседнем `metadata.json`; необычные ключи, `../`, Unicode и конфликты путей безопасны.
- GET использует исходные версию и ETag. Опись версий независимо сверяется с текущими объектами через CLI. Повторная опись и конфигурация в конце выгрузки должны
  совпасть с исходными. Изменение бакета останавливает операцию: запускать заново в спокойное время.
  Такой контроль обнаруживает видимые изменения, но не даёт атомарной копии S3 во время записи.
- Незавершённые многокомпонентные загрузки не являются объектами и не копируются.
  Недоступная для GET архивная версия приводит к ошибке; восстановление архивных объектов
  на продакшене автоматически не запрашивается.
- `checksums.json` проверяет каждый сохранённый файл; дополнительно сверяются размеры и SHA-256
  объектов. Проверка S3 выполняется без сети. Обратная загрузка бакетов этим набором не выполняется.

```sh
python3 infra/backups/s3.py verify /absolute/path/to/backup/s3
```

Основания: [pg_dumpall PostgreSQL 18](https://www.postgresql.org/docs/18/app-pg-dumpall.html),
[IAM для S3 Yandex Cloud](https://yandex.cloud/ru/docs/storage/s3/),
[ListObjectVersions](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectVersions.html).

Проверки самих скриптов:

```sh
python3 -m unittest discover -s infra/backups -p 'test_*.py' -v
sh -n infra/backups/backup-all.sh
```
