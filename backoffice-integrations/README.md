# Промышленные источники Backoffice

Установлены 4 октября 2026 на двух существующих ВМ. В Backoffice настроены:

- `control-plane` / «Инфраструктура»: 13 справочников, в том числе шард № 1 и телеметрия;
- `content-1` / «Контент · шард № 1»: 6 справочников организаций, пространств, участников,
  страниц, файлов и объёма хранения.

Accounts в эту установку не входит. Служебные источники только читаются. Личные сертификаты,
PIN, продуктовые API, миграции и данные не менялись. Дополнительных облачных ресурсов агент
не создавал; использованы секреты и правило, подготовленные владельцем.

## Схема доступа

BackofficeAPI → HTTPS/mTLS → отдельный nginx → loopback:18481 → `serve-backoffice` → PostgreSQL.
nginx и процесс чтения делят сетевое пространство. Loopback API не публикуется на хосте.
Клиенту нужны действующий сертификат отдельного машинного УЦ, отсутствие в CRL и разрешённый
серийный номер. Прокси заменяет служебные заголовки и не передаёт Cookie/Authorization.
Запись по HTTP запрещена. BackofficeAPI проверяет серверное имя и цепочку; новых публичных DNS нет.

На common nginx имеет Docker-имя `control-plane.backoffice.internal`, порт 18491 без публикации
на хост. Сеть `less-backoffice-access` связывает его с BackofficeAPI и даёт последнему маршрут
к шарду. На шарде опубликован только `10.130.0.4:18493`; правило разрешает common-services.
В Backoffice задан `extra_hosts` для `content-1.backoffice.internal` → `10.130.0.4`.
Прямое открытие этих имён браузером не предусмотрено.

Роли `backoffice_reader` отдельно созданы в controlplane и less_content: без владения, без
административных прав, без CREATE, с SELECT только на явном списке таблиц. Для shard_token,
signing_key и audit_log разрешены только столбцы, используемые справочниками. Новые таблицы
автоматически не открываются. Включены default_transaction_read_only и statement_timeout=8s;
даже после BEGIN READ WRITE запись запрещена правами.

## Файлы и запуск

На обеих ВМ `/opt/less/backoffice-integrations/compose.yml`, `prepare-host.py`.
`compose.common.yml` / `compose.shard.yml` — исходники соответствующих compose.
`prepare-host.py` доставляет только секрет данной ВМ, настраивает роль и конфигурацию;
вывод не содержит значений. Доступ к Lockbox с обеих ВМ подтверждён настоящей доставкой.
Runtime-файлы в `/etc/less/backoffice-reader`, машинные ключи и открытые сертификаты —
`/etc/less/backoffice-transport`. Ключи УЦ/пользователя туда не доставляются.

```sh
sudo docker compose -f /opt/less/backoffice-integrations/compose.yml up -d
```

Для common Backoffice штатный `/opt/less/p-common-1/compose.backoffice.yml` уже содержит
подключения, точные файловые монтирования клиентского ключа/сертификатов и сеть доступа.
Перед его первым запуском сеть создаёт compose читателя. На штатном перезапуске она сохраняется.
Резервные прежние файлы compose на common имеют суффикс `.before-source-links`.

Читатели используют существующие образы control-plane/content:latest. **При обновлении этих
образов обновлять также соответствующий контейнер reader**, чтобы чтение соответствовало схеме.
На шарде Docker Hub не ответил: nginx:1.27-alpine перенесён с common через docker save/load по SSH.
Реестр не изменялся, новых манифестов и слоёв не публиковалось.

## Обновление CRL и сертификатов

Сертификаты до **02.01.2027 17:45:32 МСК**, CRL до **11.10.2026 17:45:32 МСК**.
Автоматического выпуска CRL нет. Владелец обновляет её в исходном каталоге по
`CONSOLE-CHECKLIST.md`. Не запускать первоначальный issue-скрипт поверх существующего каталога.

После обновления агенту сообщают готовность. Доставлять нужно только открытый `ca.crl.pem`
на обе ВМ, проверить подпись и сроки, затем **пересоздать proxy и приложения вместе**
(на common — reader и accounts; на шарде — только reader):

```sh
sudo docker compose -f /opt/less/backoffice-integrations/compose.yml up -d --force-recreate proxy reader accounts
```

Причина: файлы сертификатов/CRL монтируются по отдельности; атомарная замена на хосте оставляет
старый inode внутри прежнего контейнера. Одного nginx reload после такой замены недостаточно.
После пересоздания выполнить verify-live.py. Так же менять серверные сертификаты.
При смене клиентского сертификата обновить разрешённый serial в конфигурации **обоих** прокси
через prepare-host.py и пересоздать их вместе с reader; обновить клиентское монтирование
пересозданием BackofficeAPI. Сверять сроки до операции, не удалять прежний выпуск до проверки.

## Accounts и одобрение регистраций

После `0002_registration_approval` в Accounts выполнить на common-ВМ `prepare-accounts.py`.
Он использует `less-prod-backoffice-accounts`, отдельного пользователя БД `backoffice_accounts`
и уже выпущенный сертификат `accounts.backoffice.internal`. Роль читает нужные метаданные,
может менять только `account_user.is_approved/updated_at` и добавлять задание письма; секретные
столбцы сеансов и данные авторизации ей недоступны. Это отдельная роль, поскольку PostgreSQL
общий с Control Plane, а его `backoffice_reader` остаётся только читающим.

Служба `accounts` добавлена к Compose общих источников: 0,10 CPU / 192 МиБ. Основной Accounts
получает 0,20 CPU / 576 МиБ, BackofficeAPI — 0,20 CPU / 512 МиБ. Общий предел постоянных
контейнеров на common остаётся 2 CPU / 3584 МиБ, резерв ВМ — 512 МиБ.

При замене общего proxy пересоздавать **proxy, reader и accounts вместе**: оба приложения
используют его сетевое пространство. Повторный `prepare-host.py` сохраняет подключение Accounts,
а `prepare-accounts.py` сохраняет другие подключения. После смены машинного клиента повторить
оба скрипта, чтобы оба входа получили новый разрешённый серийный номер.

Accounts слушает 18492 только внутри общей сети. nginx допускает POST лишь для
`/internal/backoffice/v1/registration-approvals/U_…/approve`; остальные справочники остаются
читающими. Снаружи новых портов и правил безопасности нет.

Промышленный `AUTH_MANUAL_REGISTRATION_APPROVAL=true`, `MAIL_MODE=disabled` до подтверждения
`less.place` в Postbox. После подтверждения заменить только `MAIL_MODE` на `smtp` и пересоздать
основной Accounts с обоими файлами `compose.services.yml` и `compose.content-shard.yml`.
Обработчик автоматически отправит накопленные уведомления. Адрес отправителя — `noreply@less.place`.

## Исправление идентификаторов одобрения — 05.10.2026

`ServeBackoffice.run()` теперь вызывает `bootstrapStrictID(config:)`, как основной Accounts.
Без этого отдельный процесс не применял переданный `STRICT_ID_SEED`: список работал,
но `UserID.parse` отклонял корректный ID при одобрении и при передаче курсора.
Пустое тело `{}` допустимо, изменение веба не требуется.

Дополнительно отсутствие пользователя возвращается из транзакции без исключения и преобразуется
в `AccountRepositoryError.accountNotFound` после её завершения: обёртка `PostgresTransactionError`
больше не превращает ожидаемый 404 в серверную ошибку. Неожиданные ошибки границы бекофиса
теперь используют только HTTP 500 вместо 503.

Проверки: `RegistrationApprovalDatabaseTests` с настоящим локальным PostgreSQL — два параллельных
одобрения создают одно уведомление; после удаления только собственной проверочной записи
повторное одобрение возвращает доменную ошибку отсутствия. `BackofficeReadBoundaryTests` проверяет
500/no-store и прежние ограничения доверенного прокси. Обе проверки прошли.
`infra/backoffice-integrations/verify-live.py` дополнен проверкой курсора по реальному ID из очереди.

Отдельный процесс Accounts обновлён локально (18482) и на p-common-1; промышленный образ
`sha256:0e7f7cca4a091c8f7974e100929e4fff1b0d5b5d52c23a4865197ca153152156`, healthy.
На обеих площадках через машинный mTLS: корректный курсор 200, неверный 400,
POST одобрения проверенного отсутствующего пользователя 404. Локальный фронтенд :80 — 200.
На промышленной площадке регистрация владельца оставлена в очереди; её одобрение не выполнялось.
Основной процесс Accounts и остальные службы не перезапускались. Промежуточный образ удалён,
образ работающего основного Accounts сохранён. Исправленные исходники перенесены из временной
копии в головной репозиторий. SMTP по-прежнему выключен, уведомления ждут включения отправки.

Владелец подтвердил успешную регистрацию после исправления OAuth/SQL от 05.10.2026.
Это подтверждает завершённую регистрацию, но не все комбинации провайдеров и способов входа.
