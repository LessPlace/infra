# Первый контентный шард: что подготовить в консоли

Проверено 04.10.2026. ВМ `p-content-shard-1` (`fv4en9lfc85kiqrn4jhi`),
внутренний адрес `10.130.0.4`, 2 CPU / 4 ГиБ / SSD 50 ГиБ. SSH через `p-common-1` работает.
Все перечисленные ресурсы подготовлены; текущее состояние — в разделе проверки ниже.
Инструкция сохранена для воспроизводимости. Облачные ресурсы создаёт владелец; значения секретов в чат не присылать.

## 1. Отдельный сервисный аккаунт ВМ

Создать `less-content-shard-1` и прикрепить к новой ВМ вместо общего `service`.
Общий аккаунт сейчас даёт новой машине права на секреты Accounts, Control Plane и Backoffice.
Новая машина должна получать только необходимые ей секреты.

Назначить **на конкретных ресурсах**, без общих ролей на каталоге:

| Ресурс | Роль для `less-content-shard-1` |
| --- | --- |
| Реестр `less-registry`, `crp5f6o2ivb58ruhp27e` | `container-registry.images.puller` |
| Существующий секрет `less-prod-content-s3`, `e6qkbdm11rko16nh13ak` | `lockbox.payloadViewer` |
| Новый секрет `less-prod-content` | `lockbox.payloadViewer` |
| Новый секрет `less-prod-content-shard-1` | `lockbox.payloadViewer` |

Это аккаунт **виртуальной машины**. Существующий `less-content-storage` остаётся отдельной
S3-личностью: его статические ключи уже лежат в `less-prod-content-s3` и дают доступ к бакету `less`.
Новый бакет и новые S3-ключи для первого шарда не нужны.

## 2. Общие секреты контентных шардов

Создать Lockbox `less-prod-content`, включить защиту от удаления.

| Ключ | Что положить |
| --- | --- |
| `STRICT_ID_SEED` | **Точная копия** одноимённого значения из `less-prod-common` |
| `AUTH_REMOTE_BEARER_TOKEN` | **Точная копия** `AUTH_INTERNAL_BEARER_TOKEN` из `less-prod-accounts` |
| `CONTENT_BEARER_TOKEN` | **Точная копия** одноимённого значения из `less-prod-accounts` |
| `CONTROL_PLANE_BEARER_TOKEN` | Один действующий токен из `AUTH_DATA_PLANE_TOKENS` секрета `less-prod-control-plane`; не операторский токен |
| `PAGE_CREATION_TICKET_PRIVATE_KEY` | Новый закрытый Ed25519-ключ в PEM, команда ниже |
| `PAGE_CREATION_TICKET_PUBLIC_KEY` | Открытый PEM от **той же пары** |

Первые четыре значения не генерировать заново: сервисы должны согласованно проверять идентификаторы
и внутренние запросы. Пара Ed25519 отдельная, не относится к пользовательским сертификатам или УЦ.
Она подписывает разрешения на создание страниц и впоследствии должна быть общей для контентных шардов.

На своём компьютере в новом закрытом каталоге:

```sh
umask 077
mkdir less-prod-page-ticket
openssl genpkey -algorithm ED25519 -out less-prod-page-ticket/private.pem
openssl pkey -in less-prod-page-ticket/private.pem -pubout -out less-prod-page-ticket/public.pem
```

Вставить в два значения Lockbox полное содержимое соответствующих файлов, включая BEGIN/END
и переводы строк. Не заменять PEM паролем, случайной строкой или ключом УЦ.
Не сохранять файлы в Git и не отправлять их в чат.

## 3. Собственные секреты шарда

Создать Lockbox `less-prod-content-shard-1`, включить защиту от удаления.

| Ключ | Что положить |
| --- | --- |
| `POSTGRES_ADMIN_PASSWORD` | Новый отдельный результат `openssl rand -hex 32` |
| `DB_PASSWORD` | Другой результат `openssl rand -hex 32`, для владельца БД `less_content` |
| `VALKEY_PASSWORD` | Ещё один результат `openssl rand -hex 32`, для прикладной ACL Valkey |

Здесь все значения новые и разные; пароли с `p-common-1` не копировать.
`SHARD_TELEMETRY_TOKEN` будет добавлен отдельной версией после регистрации шарда в Control Plane:
его выдаёт Control Plane, произвольная строка не подойдёт. Пока этот ключ **не создавать**,
не заполнять пустой строкой или заглушкой. Точную команду получения дам после регистрации.

## 4. SmartCaptcha для авторизации

Существующая капча `bpn062gug248ehea7t6s` уже разрешает `less.place`; новая не нужна.
Создать Lockbox `less-prod-smartcaptcha`, защита от удаления:

| Ключ | Что положить |
| --- | --- |
| `SMARTCAPTCHA_CLIENT_KEY` | Ключ клиента созданной капчи, начинается с `ysc1_`; он публичный |
| `SMARTCAPTCHA_SERVER_KEY` | Ключ сервера **той же капчи**, начинается с `ysc2_`; секретный |

Оба значения копируются из SmartCaptcha, а не генерируются. На этом секрете дать
`lockbox.payloadViewer` общему аккаунту `service` (`ajefiauik875043qbf7r`), который обслуживает
Accounts на `p-common-1`. Контентному шарду этот секрет и права на SmartCaptcha не нужны.
Проверка ответов пользователя выполняется серверным ключом, отдельная IAM-роль для `/validate` не нужна.
`devless.ru` в разрешённые сайты не добавлять. Для локального стенда промышленную капчу не расширяем.

## 5. Группы безопасности для связей между ВМ

Подготовить две группы в существующей VPC:

| Группа | Прикрепить к | Входящие правила |
| --- | --- | --- |
| `content-shard` | `p-content-shard-1` | TCP 1711 от группы `common-services` |
| `common-services` | `p-common-1` | TCP 7010 и отдельно TCP 1713 от группы `content-shard` |

Сначала создать обе пустые группы, затем добавить взаимные ссылки и прикрепить к ВМ.
Сохранить `ssh-client` на шарде, `ssh-gateway` на общей машине и исходящий доступ из `common-vm`.
После установки явных разрешений удалить из `common-vm` входящее **ANY от Self**:
оно сейчас разрешает все порты между всеми участниками группы и обходит желаемую изоляцию.
Порты PostgreSQL и Valkey на хостах публиковаться не будут.

Первый пробный выпуск использует HTTP с внутренними bearer-токенами только по частным адресам
между этими двумя ВМ (`APP_ALLOW_PRIVATE_PLAINTEXT_DEPENDENCIES=true`). Пользовательский HTTPS
заканчивается на edge. Переход межмашинных связей на TLS/mTLS — отдельный этап; это не машинная PKI Backoffice.

Публичный IP шарда пока оставить для исходящего доступа к реестру, Lockbox, S3 и обновлениям.
Он не используется для обслуживания пользователей. Для его удаления сначала нужны отдельная
схема исходящего NAT и маршрутизация; это не обязательное условие первого выпуска.

## Что не нужно создавать в консоли

- Ещё один бакет, реестр, публичный веб-домен или сертификат для шарда.
- Управляемые PostgreSQL/Valkey: они будут локальными контейнерами с каталогами данных на хосте.
- Роли администратора на каталог, доступ шарда к секретам Backoffice/SMTP/OAuth.
- Записи площадки/шарда и номерные блоки: это данные **нашего Control Plane**, подготовлю их отдельно.

После подготовки сообщить ID нового сервисного аккаунта и трёх секретов: `less-prod-content`,
`less-prod-content-shard-1`, `less-prod-smartcaptcha`. Сами значения не присылать.
