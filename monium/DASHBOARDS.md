## Смысл показателей

- Счётчики приложения накопительные. RPS использует `non_negative_derivative` **до** суммирования. Сброс счётчика даёт разрыв, не отрицательное значение. Первый интервал новой серии не восстанавливается; большие периоды укрупняют сетку. Это оперативная диагностика, не точный бухгалтерский подсчёт запросов.
- Процентили используют прирост бакетов `http.server.request.duration` с меткой `bin`. Для каждой службы фильтрация выполняется до `histogram_percentile`: сама функция объединяет входные серии. Это оценка внутри интервалов графика, не процентиль всех запросов за выбранный час/день.
- Цветные плитки показывают **максимальный p95 по интервалам** выбранного периода. Ориентиры: 250 мс — жёлтый, 1 с — красный, 3 с — фиолетовый. Это диагностические ориентиры, не SLA. При отсутствии запросов функция гистограммы может вернуть 0; плитки не показывают доступность службы.
- Классической тепловой карты «время × диапазон задержки» текущий интерфейс не предлагает. Использованы цветные плитки по службам и распределение по непересекающимся диапазонам. Объявленный старой схемой API тип HEATMAP в текущем интерфейсе превращается в обычную линию; он намеренно не используется. Действующий тип плиток `9` подтверждён сохранением из интерфейса и обратным чтением API.
- В общем обзоре `/health` и `/ready` исключены из нагрузки/таймингов; отдельный график считает их ответы 2xx. Подробная панель при маршруте `*` включает и эти запросы, что явно указано над графиками. Введите, например, `/registry/slice` или `/api/pages/{id}/snapshot`, чтобы сузить выбор.
- Внутренние HTTP-переходы включены. Сумма RPS нескольких служб не равна числу пользовательских действий.
- Серия 5xx появляется только после первого соответствующего ответа. Нулевая опорная линия на обзорных графиках ошибок привязана к наличию HTTP-телеметрии; она подписана отдельно. Пропавшие данные не подменяются постоянным нулём. Пустые подробные графики 4xx/5xx сверяйте с другими данными службы.
- Максимум `http.server.request.duration.max` накоплен **с запуска процесса**, и в названии соответствующего графика это явно отмечено. Для текущих задержек нужны процентили/среднее.
- Среднее время = прирост суммы длительностей / прирост количества. При нулевом количестве нового запроса среднее отсутствует.
- Метрики Compute уже выражены в процентах или в секунду: повторную производную не берём.
- Внешняя доступность сайта, nginx, браузер, SQL и зависимости не измерены отдельно. RAM и свободное место файловой системы требуют агента внутри ОС. Оповещения и SLO этой задачей не создавались.

## Воспроизведение

Версионируемый источник — `sheets-api/deploy/monium/`; рабочая копия также сохранена в `infra/monium/`.

1. `python3 build-dashboards.py` формирует три JSON-описания.
2. В отдельном окружении установить официальный пакет `yandexcloud`.
3. `python apply-dashboards.py` проверяет схему, не меняя облако.
4. `python apply-dashboards.py --apply` создаёт или обновляет только три именованные панели в указанном каталоге. Используется оператор текущего профиля `yc`, его IAM-токен остаётся только в памяти. API-ключ отправки телеметрии для этого не нужен.
5. Предыдущая конфигурация сохраняется в `dashboard-backups/`, `etag` защищает от параллельного изменения. Идентификаторы и ссылки записываются в `dashboard-manifest.json`.
6. После изменения проверить интерфейс: принятие конфигурации API само по себе не доказывает исполнение формул.
