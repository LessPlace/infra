# Backoffice на p-common-1

Адрес согласован: `https://backoffice.less.place`. Вход — личный клиентский сертификат
административного УЦ, регистрация его отпечатка в `backoffice`, затем PIN/WebAuthn.
Учётная запись Accounts и Basic Auth основного сайта здесь не используются.

## Что создаёт владелец в Яндекс Облаке

1. DNS A `backoffice.less.place` → `158.160.240.202`, если нет подходящей wildcard-записи.
2. Lockbox `less-prod-backoffice`, защита от удаления. Три ключа:

   | Ключ | Откуда взять | Назначение |
   | --- | --- | --- |
   | `DB_PASSWORD` | отдельный `openssl rand -hex 32` | пароль роли PostgreSQL `backoffice` |
   | `AUTH_PROXY_SECRET` | отдельный `openssl rand -hex 32` | подтверждение запроса от доверенного nginx |
   | `SECURITY_PIN_PEPPER` | отдельный `openssl rand -hex 32` | дополнительный секрет защиты PIN |

   Все три значения разные. Не брать их из паролей соседних сервисов и не использовать личный PIN.
   Pepper нужно сохранять вместе с резервной копией БД; не менять произвольно после настройки PIN.
   `STRICT_ID_SEED` повторно не генерировать: доставка берёт его из существующего `common.env`.
3. На **самом секрете**, а не на каталоге, роль `lockbox.payloadViewer` для сервисного аккаунта
   `service` (`ajefiauik875043qbf7r`). Агенту передать только ID секрета, значения не присылать.

Новые бакеты, реестр, серверный сертификат и сервисный аккаунт ВМ для этого не нужны.
Сертификат `less-prod` уже покрывает `*.less.place`.

## Изоляция и ограничения

- Отдельная БД и владелец `backoffice`; `PUBLIC` лишён доступа. Хранилище PostgreSQL остаётся
  привязанным к `/srv/less/postgres` на хосте. Соседние БД не мигрируются и не сбрасываются.
- `APP_CONTAINER_NETWORK=true` явно разрешает имя БД `postgres`, привязку API к `0.0.0.0`
  внутри контейнера и точные частные IPv4 прокси. По умолчанию остаётся только loopback.
- API не публикует порт на хост. Закрытая сеть `less-backoffice`, `172.30.10.0/24`:
  edge `.2`, API `.3`, веб `.4`. Только `.2` доверен API; дополнительно обязательны секрет,
  подтверждение TLS, корректный сертификат и действующие права в БД.
- Общий предел восьми контейнеров: **1,95 CPU / 3392 МиБ**. BackofficeAPI 0,25 CPU / 512 МиБ,
  BackofficeWeb 0,05 CPU / 64 МиБ; Control Plane 0,20 CPU / 512 МиБ,
  Accounts 0,25 CPU / 768 МиБ. Остальные пределы прежние.
- `devless.ru` и его поддомены остаются закрытыми; основной `less.place` сохраняет Basic Auth.

## Подготовка и установка

Lockbox создан владельцем: `e6qqr1fb97513kums3vu`, ACTIVE, защита от удаления и точечная роль
ВМ проверены. DNS указывает на `158.160.240.202`. БД/роль созданы без изменения соседних БД.

Образы собираются локально `--platform linux/amd64`, публикуются в существующем реестре
как `backoffice-api:latest` и `backoffice-web:latest`, с `--provenance=false`, чтобы не создавать
служебные манифесты с дополнительными тегами. Серверный образ включает ресурс `0001.sql`.
`publish-service.py` и `registry-pull.py` поддерживают оба имени.

`deliver-backoffice-pki.py` запускается на рабочем компьютере: проверяет сроки и подписи,
доставляет только открытые сертификаты корня/административного УЦ и CRL в
`/etc/less/backoffice-pki`. Закрытые ключи УЦ и пользователей не читает.
После обновления CRL выполнить этот скрипт и `nginx -t`, затем `nginx -s reload` внутри edge.
CRL необходимо обновлять до истечения срока; автоматического выпуска владельцем УЦ пока нет.

На ВМ после загрузки конфигурации и доставки основного `common.env`:

```sh
sudo python3 /opt/less/p-common-1/prepare-backoffice.py --secret-id ID_СЕКРЕТА
sudo python3 /opt/less/p-common-1/registry-pull.py backoffice-api
sudo python3 /opt/less/p-common-1/registry-pull.py backoffice-web
```

Подготовка создаёт только отсутствующие БД/роль, не меняет существующий пароль. Затем сначала
применить уменьшенные ограничения `compose.services.yml` и проверить здоровье соседних служб;
только после этого запускать Backoffice. Миграция и первый администратор:

```sh
cd /opt/less/p-common-1
sudo docker compose -f compose.backoffice.yml run --rm --no-deps backoffice-api migrate
sudo docker compose -f compose.backoffice.yml run --rm --no-deps backoffice-api \
  bootstrap-root --handle kirill --name 'Кирилл Титов'
sudo docker compose -f compose.backoffice.yml up -d
```

ID `AU_…` и SAN брать из вывода промышленной команды. Не предполагать совпадение с локальным
администратором: оно зависит от общего `STRICT_ID_SEED`. Личный сертификат выпускает владелец УЦ;
агент регистрирует только открытый `.cert.pem`. Закрытый ключ и `.p12` на ВМ не передаются.
Для выпуска владельцем УЦ подготовлен `issue-backoffice-admin.py --user-id AU_… --name 'Кирилл Титов'
--output-dir /absolute/new/directory`. Он использует штатный выпуск сертификата, но проверяет
учётную запись и регистрирует открытый сертификат через SSH на ВМ. Ключ и `.p12` остаются локально.
Владелец выполнил настоящий выпуск и подтвердил успешную регистрацию и вход. Локальный
`issue-admin-certificate.py` по умолчанию продолжает работать только с локальной БД.

Edge запускается с **обоими** файлами:

```sh
sudo docker compose -f compose.edge.yml -f compose.edge-backoffice.yml up -d
sudo docker compose -f compose.edge.yml exec -T edge nginx -t
```

Все будущие `up` для edge также должны учитывать второй файл, иначе исчезнет вход админки.
Существующий таймер сертификата использует `exec`, поэтому дополнительных файлов ему не нужно.

## Отдельный оставшийся этап: продуктовые источники

Первоначально `BACKOFFICE_INTEGRATIONS_FILE` пуст: интерфейс честно показывает отсутствие источников.
Для чтения Control Plane и Accounts нужны отдельные процессы `serve-backoffice`, роли PostgreSQL
только для чтения, секреты служебных прокси и промышленная машинная ветвь PKI с CRL.
Локальный самоподписанный машинный УЦ переносить в промышленную среду нельзя.
Пользовательский сертификат не является машинным сертификатом сервиса.
Контент-шарды подключаются после их появления. Дополнительные процессы требуют нового расчёта
общих лимитов до запуска; текущий бюджет относится только к восьми указанным контейнерам.
