## 1. Бакет аватаров и две учётные записи S3

Accounts по существующему договору использует отдельный бакет. Общий `less` ему не назначаем.

1. Создать закрытый бакет `less-accounts-prod` класса STANDARD. Если имя занято глобально,
   выбрать другое и сообщить его. Начальное ограничение объёма — 5 ГиБ.
2. Создать сервисные учётные записи `less-accounts-storage` и `less-content-storage` без общих
   ролей на каталог. Первая работает только с аватарами, вторая — только с `less`.
3. В каждом соответствующем бакете задать политику доступа по шаблону `bucket-policy.example.json`:
   подставить имя бакета, ID его сервисной учётной записи и ID владельца-оператора. Политика
   разрешает сервису чтение, запись, удаление объектов и составные загрузки, но не изменение
   настроек или удаление бакета. Правило владельца сохраняет его доступ через консоль.
   Не назначать сервису общие роли на каталог. Одного `storage.uploader` недостаточно:
   эта роль **не разрешает удаление объектов**, необходимое для уборки аватаров.
4. Дополнительно выдать каждой сервисной учётной записи ACL `READ` и `WRITE` **только на её бакет**.
   Одной политики недостаточно: сначала запрос проходит IAM/ACL, затем bucket policy.
   Исправление первоначальной инструкции по результату живого `403 AccessDenied` от 4 октября.
   Подготовленная команда для обоих бакетов — `fix-bucket-access.sh`; запускать после согласования
   изменения прав. [Алгоритм Яндекса](https://yandex.cloud/ru/docs/storage/security/overview).
5. Выпустить для каждой учётной записи отдельный **статический ключ доступа**. Сохранить
   идентификатор ключа и секретный ключ в соответствующий секрет Lockbox ниже. Секретный ключ
   показывается при выпуске; не отправлять его в чат и не записывать в Git.
6. Публичное чтение и просмотр списка объектов оставить выключенными. Доступ браузеров к файлам
   позже обеспечит приложение; открывать бакет для всех не требуется.

`REPLACE_OWNER_USER_ID` — идентификатор вашей личной учётной записи в Яндекс Облаке.
Правило `KeepOwnerAccess` сохраняет ей полный доступ к этому бакету. Узнать ID можно командой
`yc iam whoami`, выполнив её под своей учётной записью, либо в Identity Hub → Пользователи →
Идентификатор. Проверено 4 октября: текущий пользователь `yc` — `aje3tuu3u7it92n56qli`.
Это значение можно подставить в обе политики. В `REPLACE_SERVICE_ACCOUNT_ID` для каждой политики
подставляется ID соответствующей сервисной учётной записи, а не её статического ключа.

Адрес S3: `https://storage.yandexcloud.net`, регион подписи: `ru-central1`.
После выдачи прав проверим запись, чтение и удаление только собственного пробного объекта,
а также отказ при обращении чужой учётной записью. Для прямых загрузок контентных файлов
в бакете `less` обязательно правило CORS: только `https://less.place`, методы PUT/GET/HEAD,
заголовки content-type/content-length/range, открытый ответный заголовок ETag, кэш 300 секунд.
Правило установлено 05.10.2026; команда и проверки — в `infra/p-content-shard-1/README.md`.
Для серверных аватаров CORS не нужен; публичный доступ к бакетам остаётся выключенным.

[Права на отдельный бакет](https://yandex.cloud/ru/docs/storage/operations/buckets/iam-access),
[роли Object Storage](https://yandex.cloud/ru/docs/storage/security/).

## 2. Lockbox: что генерировать и откуда брать значения

Уточнено 4 октября 2026 по текущему коду сервисов и выбору Yandex Cloud Postbox.

В этом разделе **секрет** — именованный объект Lockbox, например `less-prod-common`.
Внутри него несколько **полей**: имя поля вводится в колонку «Ключ», его значение — в
колонку текстового значения. Сейчас нужны шесть пользовательских секретов из подразделов 2.1–2.6;
седьмой, для OAuth, создадим после получения настоящих реквизитов;
уже созданные повторно не создавать. Для каждого
включить защиту от удаления. Имена секретов и полей копировать точно, с сохранением регистра.

Значения бывают трёх видов:

- **Сгенерировать самостоятельно** — пароли БД, служебные токены, StrictID seed и ключи Accounts.
- **Скопировать из Яндекс Облака** — статические ключи S3 и API-ключ Postbox.
- **Отложить создание** — секрет OAuth, пока нет настоящих реквизитов внешних поставщиков.
  Lockbox отклоняет пустые значения, в том числе через `yc`.

### Как сгенерировать случайное значение

Для каждого поля с пометкой **«Сгенерировать hex»** выполнить на своём Mac:

```sh
openssl rand -hex 32 | tr -d '\n' | pbcopy
```

Команда создаёт 32 криптографически случайных байта, записывает их в виде строки из
64 шестнадцатеричных символов и копирует строку в буфер обмена. Вставить её в значение
**одного** поля Lockbox. Для следующего такого поля выполнить команду заново — получится
другое значение. Всего ниже десять таких полей. Не использовать один результат во всех полях.
Если поле уже заполнено подходящим случайным значением, заново генерировать его не нужно.

Только для `AUTH_OAUTH_CIPHER_KEY` нужна другая команда:

```sh
openssl rand -base64 32 | tr -d '\n' | pbcopy
```

Она также создаёт 32 случайных байта, но кодирует их в Base64. Вставить результат целиком,
включая завершающий `=`. Это один отдельный ключ; hex-строка из первой команды сюда не подходит.
Команды сами ничего не создают в облаке: они лишь кладут значение в буфер обмена.

### 2.1. Секрет `less-prod-common`

Все пять значений генерируем сами. Яндекс их не выдаёт: PostgreSQL и Valkey будут работать
в наших контейнерах. При первоначальной настройке назначим им именно эти пароли из Lockbox.

| Поле | Что записать | Для чего |
| --- | --- | --- |
| `POSTGRES_ADMIN_PASSWORD` | Сгенерировать hex | Пароль администратора общего PostgreSQL; приложения его не используют |
| `CONTROLPLANE_DB_PASSWORD` | Сгенерировать hex отдельно | Пароль пользователя БД `controlplane` |
| `ACCOUNTS_DB_PASSWORD` | Сгенерировать hex отдельно | Пароль пользователя БД `less_accounts` |
| `VALKEY_ACCOUNTS_PASSWORD` | Сгенерировать hex отдельно | Пароль отдельного пользователя Accounts в Valkey |
| `STRICT_ID_SEED` | Сгенерировать hex отдельно, один раз для этого окружения | Общий секрет настройки кодирования идентификаторов |

`STRICT_ID_SEED` передадим одним и тем же значением в Control Plane, Accounts и будущие
контентные сервисы. Для каждого сервиса новый seed **не** генерировать. После появления данных
его нельзя менять как обычный пароль: это требует отдельного плана перехода.

### 2.2. Секрет `less-prod-control-plane`

**Да, `AUTH_OPERATOR_TOKENS` и `AUTH_DATA_PLANE_TOKENS` — обычные случайные секретные строки,
которые генерируем сами.** Это не IAM-токены Яндекса, не JWT и не ключи из какого-либо кабинета.

| Поле | Что записать | Для чего |
| --- | --- | --- |
| `AUTH_OPERATOR_TOKENS` | Сгенерировать hex | Доступ оператора к административным операциям Control Plane |
| `AUTH_DATA_PLANE_TOKENS` | Сгенерировать hex отдельно | Доступ прикладных сервисов к Control Plane с другим классом прав |

Несмотря на множественное число `TOKENS`, сейчас в каждое поле вставить **одну строку**.
Без кавычек, квадратных скобок и префикса `Bearer `. Эти две строки обязательно должны
различаться: одинаковые значения код отклоняет. Оба поля нужны даже до появления шардов.

Код допускает несколько токенов в одном поле через запятую — это пригодится при замене
ключей. Сейчас список не нужен. Сервису, который обращается к Control Plane, позже передадим
один из уже записанных токенов соответствующего класса, а не сгенерируем несвязанный новый.
Токены heartbeat отдельных шардов выдаются отдельно; эти поля их не заменяют.

### 2.3. Секрет `less-prod-accounts`

| Поле | Что записать | Для чего |
| --- | --- | --- |
| `AUTH_EMAIL_LINK_PEPPER` | Сгенерировать hex | Секрет для защиты одноразовых почтовых ссылок; это не пароль почтового ящика |
| `AUTH_INTERNAL_BEARER_TOKEN` | Сгенерировать hex отдельно | Токен, которым другие наши сервисы будут авторизоваться во внутреннем API Accounts |
| `CONTENT_BEARER_TOKEN` | Сгенерировать hex отдельно | Токен, которым Accounts будет обращаться к внутреннему API контентного сервиса |
| `AUTH_OAUTH_CIPHER_KEY` | Сгенерировать **Base64** второй командой выше | Ключ шифрования временных данных OAuth; после декодирования должно быть ровно 32 байта |

Эти значения можно создать сейчас, хотя вход пока отключён. Они не выдаются VK, Яндекс ID
или почтовым сервисом. Два токена с `BEARER_TOKEN` тоже хранить без префикса `Bearer `.

При настройке принимающей стороны используем тот же соответствующий токен:
`AUTH_INTERNAL_BEARER_TOKEN` — у клиентов Accounts, `CONTENT_BEARER_TOKEN` — у принимающего
контентного сервиса. Это **два разных** секрета, и ни один не заменяет токены Control Plane.

### 2.4. Секрет `less-prod-accounts-s3`

Здесь ничего случайного самостоятельно не генерируем. В консоли открыть сервисную учётную
запись `less-accounts-storage` из пункта 1 и выпустить для неё **статический ключ доступа**,
если он ещё не выпущен. Скопировать два значения из результата выпуска:

| Поле Lockbox | Что скопировать из Яндекс Облака |
| --- | --- |
| `S3_ACCESS_KEY` | Идентификатор статического ключа доступа — Access Key ID |
| `S3_SECRET_KEY` | Секретный ключ — Secret Access Key |

Это именно ключ для S3: ID самой сервисной учётной записи, IAM-токен и авторизованный JSON-ключ
сюда не подходят. Секретная часть показывается при выпуске — сразу сохранить её в Lockbox.

### 2.5. Секрет `less-prod-content-s3`

Повторить действия предыдущего подпункта для **другой** сервисной учётной записи —
`less-content-storage`, которой разрешён доступ к бакету `less`.

| Поле Lockbox | Что скопировать из Яндекс Облака |
| --- | --- |
| `S3_ACCESS_KEY` | Access Key ID статического ключа `less-content-storage` |
| `S3_SECRET_KEY` | Secret Access Key из того же выпуска |

Названия полей совпадают с предыдущим секретом, значения — другие. Сохраняем для будущих

### 2.6. Секрет `less-prod-mail-sender` — Yandex Cloud Postbox

По сообщению владельца от 4 октября уже созданы сервисная учётная запись `postbox-user`
с ролью `postbox.sender`, API-ключ и этот секрет. Домен пока проходит проверку.
Отдельный секрет `less-prod-smtp` из прежней редакции инструкции больше не требуется.

| Поле Lockbox | Что записать | Куда передать при развёртывании Accounts |
| --- | --- | --- |
| `ID` | Идентификатор **API-ключа**, не ID учётной записи `postbox-user` | `MAIL_SMTP_USERNAME` |
| `KEY` | Секретная часть того же API-ключа, без преобразований | `MAIL_SMTP_PASSWORD` |

У API-ключа должна быть область действия `yc.postbox.send`. Учётная запись `postbox-user`
и адрес Postbox должны находиться в одном каталоге. Для API-ключа вычислять отдельный SMTP-пароль
не нужно; инструкция преобразования статического ключа доступа к нему не относится.

Остальные параметры задаются в конфигурации Accounts, хранить их в Lockbox необязательно:

| Параметр | Значение |
| --- | --- |
| `MAIL_MODE` | `smtp` |
| `MAIL_SMTP_HOSTS` | `postbox.cloud.yandex.net` |
| `MAIL_SMTP_PORT` | `587` |
| `MAIL_SMTP_TLS` | `starttls` |
| `MAIL_FROM_ADDRESS` | `noreply@less.place` — выбран владельцем 4 октября; ждём подтверждения домена |
| `MAIL_FROM_NAME` | `Лес` |

Текущий SMTP-клиент Accounts уже поддерживает STARTTLS и `AUTH LOGIN`, а логин принимает
как строку. Отдельный программный модуль для Postbox по этим требованиям не нужен.
При развёртывании ещё нужно реализовать получение `ID`/`KEY` из Lockbox и передачу в указанные
параметры: приложение само эти имена полей Lockbox не читает. Пока домен не подтверждён,
доставку не считаем проверенной. В рамках этой настройки письма не отправлялись.

Источник: [отправка через Postbox по SMTP](https://yandex.cloud/ru/docs/postbox/operations/send-email).

### 2.7. Секрет `less-prod-oauth`

**Обновление 4 октября:** секрет создан с четырьмя настоящими реквизитами, проверен и подключён.
VK и Яндекс включены; инструкция ниже об отсутствии значений описывает первоначальную установку.

Не использовать пробелы, случайные строки или фиктивные реквизиты вместо отсутствующих ключей.

| `OAUTH_VK_CLIENT_ID` | Не создавать | ID приложения в кабинете VK ID |
| `OAUTH_VK_SERVICE_TOKEN` | Не создавать | Сервисный ключ доступа того же приложения VK ID |
| `OAUTH_YANDEX_CLIENT_ID` | Не создавать | ClientID приложения в кабинете Яндекс OAuth |
| `OAUTH_YANDEX_CLIENT_SECRET` | Не создавать | Client secret того же приложения Яндекс OAuth |

Порядок создания приложений и точные адреса возврата — в пункте 4 ниже. Приложение Яндекс ID
создаётся в кабинете OAuth, а не среди сервисных учётных записей Яндекс Облака.

## 4. VK ID и Яндекс ID — когда понадобится вход

Полная инструкция уже есть в `less-accounts-api/docs/oauth-setup.md`. Для этого развёртывания:

| Настройка | Значение |
| --- | --- |
| `APP_PUBLIC_ORIGIN` и `OAUTH_PUBLIC_BASE_URL` | `https://less.place` |
| Адрес возврата VK | `https://less.place/api/accounts/v1/oauth/vk/callback` |
| Адрес возврата Яндекса | `https://less.place/api/accounts/v1/oauth/yandex/callback` |
| Домен VK | `less.place` |
| Исходящий IP сервера VK | `158.160.240.202` — перепроверить, если меняется сеть или адрес |

**VK ID:** в [кабинете VK ID](https://id.vk.ru/about/business/go/) создать и подтвердить профиль,
создать Web-приложение, указать домен и адрес возврата выше. Для серверного обмена выбрать
конфиденциальный режим, разрешить исходящий IP, включить получение почты. Сохранить ID приложения
в `OAUTH_VK_CLIENT_ID`, сервисный ключ доступа — в `OAUTH_VK_SERVICE_TOKEN`. Защищённый ключ
`client_secret` не является заменой сервисному ключу в текущем коде Accounts. Используемые права:
`vkid.personal_info email`.

**Яндекс ID:** в [кабинете OAuth](https://oauth.yandex.ru/client/new/id/) создать приложение для
авторизации пользователей, выбрать веб-сервис, указать название, контактную почту, значок и
адрес возврата выше. Дать права на почту и имя пользователя (`login:email`, `login:info`).
Сохранить ClientID и Client secret в `OAUTH_YANDEX_CLIENT_ID` и `OAUTH_YANDEX_CLIENT_SECRET`.
Тестовое приложение создавать отдельно, не добавлять localhost в боевое.

После заполнения Lockbox нужны повторное развёртывание Accounts и проверка входа с реальными
провайдерами. Сегодня вход намеренно не включается. Названия разделов кабинетов могут меняться;
провайдерские страницы не удалось повторно прочитать автоматическим просмотром 30 сентября,
поэтому шаги опираются также на существующую проверенную инструкцию проекта.

## 5. Что можно отложить

- `less-backups` подходит для будущих резервных копий PostgreSQL: логические копии либо
  полноценное архивирование WAL с инструментом резервного копирования. Копировать работающий
  каталог PostgreSQL как обычные файлы нельзя. Сначала выберем сроки хранения, расписание и
  проверку восстановления. Права приложений на `less-backups` не выдаём.
- Автоматическую очистку реестра настраиваем после определения хранения предыдущей версии.
  Удаление по отсутствию обычного тега не должно затронуть дочерние манифесты текущего образа.
  Сейчас загружен один выпуск веба, около 23 МБ сжатых слоёв; старых выпусков для удаления нет.
- Smart Web Security / WAF / балансировщик пока не создавать. Расчёт и выбор — в `WAF-COST.md`.
- В Billing создать бюджет с уведомлениями, например при 50/80/100% согласованной суммы.
  Это только уведомления: [бюджет не останавливает потребление](https://yandex.cloud/ru/docs/billing/concepts/budget).
